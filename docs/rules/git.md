# git.md — 브랜치 / 커밋 / PR / 머지 (3인 바이브코딩 협업)

> 전략: **GitHub Flow 뼈대 + 짧은 브랜치·잦은 머지(TBD 규율).**
> 바이브코딩의 두 리스크 — ① AI가 짠 코드끼리 부딪히면 머지 충돌을 풀기 어렵다, ② 사람이 한 줄씩 안 본 코드라 검증이 약하다 — 를 막는다.
> 세 기둥: (1) PR 리뷰 유지, (2) 브랜치는 짧게·자주 머지, (3) CI(static-analysis)가 생명줄.
> 가드레일·절대규칙은 `CLAUDE.md`가 상위. 이 문서는 git 흐름만 다룬다.

## 🚫 절대 규칙
1. **`main`에 직접 커밋/푸시 금지.** 모든 변경은 브랜치 → PR.
2. **사람 리뷰 승인 없이 머지 금지.** (Codex 클라우드 리뷰는 제안만 — 머지 못 막음)
3. **CI 빨간불로 머지 금지.** = `static-analysis`(Checkstyle+PMD+ArchUnit) + 빌드·테스트 초록이어야 함.
   - "배포 가능"의 정의 = 빌드 + `apps/api: ./gradlew check` + `apps/ingest: pytest` 통과. (커버리지 % 게이트는 두지 않는다)
4. **며칠짜리 거대 브랜치 금지.** 잘게 못 쪼갰다는 신호.
5. **한 PR에 여러 앱/남의 영역을 섞지 않는다.** PR은 본인 작업 단위(FR/AC)로 작게.
6. **계약 문서(PRD·AC·data-model·api-spec) 변경을 코드 PR에 슬쩍 섞지 않는다.** 특히 `data-model.md`는 **LOCKED(3인 합의)**.

## 브랜치
- `main`에서 새 브랜치를 따서 시작한다. 수명 **하루 미만** 목표.
- 무관한 변경을 한 브랜치에 섞지 않는다. 자주 `main`을 당겨와 rebase 한다.

### 네이밍 — `{타입}/{앱-간단설명}`
```
feat/ingest-bizinfo-source
feat/api-opportunity-list
fix/api-dday-calc
docs/ac-fr001-sync
```
타입: `feat` · `fix` · `refactor` · `test` · `chore` · `docs` (커밋 타입과 동일 집합)

## 커밋 — Conventional Commits (한글, 이미 사용 중)
형식: `{타입}(scope): {설명}` — scope는 앱/문서(`api`·`ingest`·`web`·`AC` 등), 생략 가능.
```
feat(ingest): K-Startup 수집 파이프라인 추가
fix(api): dDay 계산에서 상시모집 null 처리
docs(AC): FR-001 라이브 검증 결과 반영
chore: .gitattributes 줄바꿈 정책 추가
```
- 작게·자주. 하나의 커밋 = 하나의 논리적 변경.
- 제목 명령형·현재형, 50자 이내 권장. "왜"가 자명하지 않으면 본문에 적는다.
- 포맷/리네임만 바꾼 커밋과 로직 커밋을 섞지 않는다.

## Pull Request (생략 금지)
바이브코딩일수록 PR은 **AI가 짠 코드를 사람이 거르는 관문**이다. 가능하면 변경 400줄 이내.

### PR 설명 템플릿 (반드시 채운다)
```markdown
## 무엇을 / 왜
(이 PR이 하는 일 한두 줄 + 배경)

## 어떻게
(주요 변경점. 새 API/마이그레이션/소스가 있으면 명시)

## 영향 범위 (체크)
- [ ] 계약 문서(PRD·AC·data-model·api-spec)를 건드렸는가? (data-model은 LOCKED — 3인 합의 사유:)
- [ ] Flyway 마이그레이션을 추가했는가? (타임스탬프 버전명 / 기존 파일 미수정 확인)
- [ ] 새 의존성을 추가했는가? (사유:)
- [ ] 절대규칙 영향 없음 확인 — status 저장 / raw 가공 / is_canonical 누락 / 필드명·enum 변경 / "받을 수 있어요" 카피 / Out-of-Scope 기능

## 테스트
(추가한 테스트. apps/api=Spring, apps/ingest=pytest, apps/web=AC 수동 절차)

## AC
- [ ] 완료 선언 시 `AC.md` §1 매핑 테이블 상태 칸을 같은 커밋에서 갱신
```

### 머지 전 체크리스트
1. CI(static-analysis + 빌드 + 테스트)가 전부 초록인가?
2. 본인 앱/영역 + 합의된 공통만 건드렸는가?
3. 새 마이그레이션이 기존 파일을 수정하지 않고 새 버전으로 추가됐는가?
4. 새 의존성을 임의로 넣지 않았는가?
5. 사람 리뷰 승인을 받았는가?

## 머지 방식
- **Squash merge** 기본 (하루살이 브랜치의 잡 커밋을 하나로). 머지된 브랜치는 삭제.

## 충돌 예방 (3인 동시 작업의 핵심)
1. **본인 앱/영역 안에서만 작업한다.** 앱 분리(api/ingest/web)가 코드 충돌을 구조적으로 줄인다.
2. **Flyway 마이그레이션은 타임스탬프 버전명**을 쓴다 → 동시에 만들어도 버전번호가 충돌하지 않는다.
   ```
   V20260612_1430__create_xxx.sql      # V + yyyyMMdd_HHmm + __설명
   ```
   - 위치: `/db/migrations` (Flyway가 여기를 바라봄). 순번(V1, V2…)은 3인 동시 작성 시 충돌하므로 **신규 파일부터 타임스탬프**를 쓴다.
   - 이미 머지된 마이그레이션은 **수정·삭제 금지**. 항상 새 버전 파일을 추가한다.
3. 공통/계약 변경은 짧게 끝내고 빨리 머지해 남이 오래 기다리지 않게 한다.
