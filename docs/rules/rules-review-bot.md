# 리뷰봇 위임 기준 (rules-review-bot.md)

> 어떤 규칙을 봇에 맡기고 어떤 규칙을 사람에게 남길지의 기준.
> 원칙: **셀 수 있는 규칙은 봇, 의미·설계 판단이 필요한 규칙은 사람.**
> 봇에 의미 판단을 시키면 오탐이 쏟아져 신뢰를 잃는다. 신뢰를 잃은 봇은 무시당한다.

## A. 봇에 위임 (자동 차단 가능 / 오탐 거의 없음)
기계적으로 셀 수 있어 봇이 가장 잘하는 영역. 사람 리뷰에서는 빼도 된다.

- indent depth > 2
- 메서드 라인 수 > 20
- 메서드 인자 수 > 4
- 인스턴스 변수 > 5
- `else` / `switch`-`case` / 삼항 연산자 사용
- 축약·약어, 한 글자 변수명
- 네이밍 컨벤션(케이스, 길이)
- 배열 사용(컬렉션 권장 위치)
- 디미터 위반 중 **체이닝 형태**(`a.getB().getC()`)만 — 패턴으로 탐지 가능

→ 이 항목들은 CI에서 정적 분석(Checkstyle/PMD/ArchUnit 등)으로 **하드 게이트** 처리 권장.

## B. 사람 리뷰 전용 (봇에 넣지 말 것)
의미·맥락 판단이 필요해 봇이 오탐/미탐을 낸다. 봇에 넣으면 노이즈가 되어 A의 신뢰까지 깎는다.

- **SRP** — "변경 이유가 다르면 분리" (봇이 변경 이유를 모른다)
- **Tell, Don't Ask** — "데이터를 꺼내 외부에서 판단했는가" (의미 분석 필요, 체이닝과 별개)
- **다형성 전환 시점** — "같은 분기 2곳↑" 판단은 의도 파악 필요
- **추상화 레벨 결정** — "상위에서 구현"이 적절한지
- **불변 여부** — "변경 여지가 없다면"의 조건 판단
- **트랜잭션 묶음 경계** — 정합성을 타이트/느슨 중 무엇으로 볼지
- **테스트가 행위 완결성을 검증하는지** (커버리지 수치로는 못 잡음)

## C. 조건부 (LLM 리뷰봇이면 가능, 정적 분석은 불가)
LLM 기반 봇이라면 **경고(non-blocking)** 수준으로만. 차단은 사람이.

- 성급한 추상화(분기 1곳인데 인터페이스 도입)
- 원시값 포장 누락 중 "도메인 의미가 있어 보이는" 값
- Null Object로 바꿀 만한 null 반환

→ LLM 봇은 **차단하지 말고 제안만** 하게 한다. 근거가 약한 차단은 무시·우회를 부른다.

## 운영 원칙
1. **하드 게이트(A)와 소프트 제안(C)을 분리**한다. 섞으면 둘 다 무뎌진다.
2. 봇 지적의 **오탐률을 측정**한다. 특정 규칙의 오탐이 높으면 B로 내리거나 C로 완화한다.
3. **위반 로그를 쌓는다.** 자주 어기는 규칙 = `rules-core.md` 상시 주입 후보, 한 번도 안 어기는 규칙 = 상시본에서 제외 후보.
