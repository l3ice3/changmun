# persistence.md — 저장·트랜잭션·멱등성 규칙

> **무엇을 함께 저장하고, 어디까지 묶고, 실패하면 어떻게 안내할지**에 대한 약속.
> 설계(`.claude/rules/rules-core.md`·`rules-full.md` §6·§7)·테스트(`testing.md` 5절)·계약(`docs/data-model.md` LOCKED)과 함께 읽는다.
> 창문은 **읽기 전용 서빙 API + 일 1회 수집 배치** 구조라, 트랜잭션의 무게중심은 `apps/api`가 아니라 **`apps/ingest`(UPSERT 배치)**에 있다.

## 1. 도메인 ↔ 저장소 분리

- **도메인은 DB를 직접 알지 않는다.** Repository 인터페이스로 통신을 감싼다. 도메인 객체에 SQL·JPA가 새어 나오지 않게 한다.
- **Repository는 Service 계층 안에서만 다룬다.** 컨트롤러·도메인·뷰는 Repository를 모른다 (ArchUnit이 검사 — `ArchitectureTest.java`).
- 영속성 기술이 바뀌어도 도메인 규칙이 흔들리지 않아야 한다.
- **스키마의 단일 진실은 `/db/migrations` Flyway**다. ORM이 스키마를 만들지 않는다 — `ddl-auto=validate` 고정(절대규칙 1). 엔티티가 스키마와 안 맞으면 **기동 실패가 정답**(엔티티를 고친다).

## 2. 계산값은 저장하지 않는다 (창문 핵심)

- **`status`·`dDay`·`closingSoon`·`badges`는 저장 금지.** 마감일 기준으로 **조회 시 서버가 계산**한다(절대규칙 2, 산식=`api-spec.md §0`).
- 파생값을 저장하면 "오늘"이 지나는 순간 거짓이 된다. 저장하는 건 **원천 속성**(`application_deadline`, `is_always_open` 등)뿐.
- `raw` 컬럼은 **원본 그대로** — 가공·요약해서 저장 금지(절대규칙 3).

## 3. 작업 단위(Unit of Work)의 경계 — 무엇을 하나로 묶나

판단 기준은 단 하나: **"일부만 성공한 중간 상태가 사용자/다음 단계에 거짓을 보여주는가."**

- **묶는다 (하나의 트랜잭션)** — 한 작업 안에서 둘 이상을 바꾸고, 그것들이 **함께 성립해야만** 모순 없는 상태가 될 때.
- **묶지 않는다** — 변경이 하나뿐이거나, 여러 변경이라도 서로의 정합성에 영향을 주지 않는 **부수 효과**(로그·통계·캐시). 부수 효과는 트랜잭션 경계 밖으로 뺀다. 곁다리(로그 실패)가 본질(데이터 적재)을 롤백시키면 안 된다.

**경계를 정하는 순서:** ① 실패하면 다음 단계가 보는 데이터가 거짓이 되는가? → 묶는다 / ② 실패해도 본질이 멀쩡하고 나중에 복구 가능한가? → 뺀다.

### 창문의 작업 단위 예시
- **레코드 UPSERT** — `(source, external_id)` 한 건의 적재는 그 자체가 최소 단위. 부분 저장이 없다(아래 5절 멱등성).
- **dedup 그룹 → canonical 지정** — 한 그룹 안에서 대표(`is_canonical=true`) 지정과 멤버 연결은 **함께 성립**해야 리스트 서빙(절대규칙 4: canonical만 노출)이 거짓을 안 보여준다 → 정합성 단위로 묶는다.
- **event_log** — append-only **부수 효과**다. 본질을 롤백시키지 않도록 경계 밖에서 다룬다(6절).
- **소스별 수집** — 소스 간에는 **격리**한다. 한 소스 트랜잭션 실패가 다른 소스를 롤백시키면 안 된다(AC-004).

## 4. 소스·레코드 단위 장애 격리 (ingest)

- **소스 장애 격리** — 한 소스 실패가 다른 소스 수집을 막지 않는다 (AC-004). 소스별로 경계를 닫는다.
- **레코드 단위 오류는 스킵 + 로그** — 한 레코드의 필수필드 누락/파싱 실패가 배치 전체를 죽이지 않는다 (AC-003). 배치는 계속된다.
- **미지 enum → '기타' + 원본 로그** — 열린 enum 원칙. 새 값에 crash 금지 (AC-005).
- 실행 결과 리포트: 소스별 신규/갱신/스킵/미지값 건수 (DoD).

## 5. 멱등성 — DB가 보장한다 (코드가 아니라)

> 창문 절대규칙(ingest 규칙 3)의 근거이자 가장 중요한 절.

- **재시도가 항상 옳은 건 아니다.** "조회 후 처리"는 그 자체가 경쟁(race)에 노출된다. 멱등성은 **애플리케이션의 사전 조회가 아니라 DB의 원자적 제약·UPSERT 같은 단일 직렬화 지점**에서 보장한다.
- **창문의 못 박기:** `(source, external_id)` **UNIQUE** + `INSERT ... ON CONFLICT (source, external_id) DO UPDATE` (UPSERT). 코드에서 `SELECT 존재 확인 후 INSERT`하는 패턴은 **금지**(레이스로 중복 생성).
- 재실행 시 동작: 행 수 불변, `updated_at`만 갱신, **`first_seen_at`은 불변**(최초 관측 시각 보존) (AC-002).
- **외부 부수 효과**(이미 호출한 외부 API)는 되돌릴 수 없어 멱등성에 한계가 있다 → 본질 적재와 분리하고, 재실행해도 안전하도록 설계한다(타임아웃+재시도 N회 — `ingest.md` 규칙 8).

## 6. 부수 효과 — event_log (append-only)

- event_log는 **익명 UUID + 화이트리스트 payload 키만**. PII 필드 자체가 스키마에 없어야 한다(절대규칙 6, AC-027).
- **로깅은 본질을 막지 않는다.** 프론트는 fire-and-forget(await 금지, 에러 무시 — AC-026, `web.md` 7). 서버 쓰기도 본질 트랜잭션 밖.
- append-only — 기록은 추가만 한다. 갱신·삭제로 이력을 바꾸지 않는다.

## 7. 저장 시점

- 시스템 상태가 바뀌는 **최소 유효 단위마다** 영속화한다(장애 시 유실·중간 상태 최소화).
- 단, 묶지 않아도 되는 것을 한 트랜잭션에 끌어모아 길게 잡지 않는다(3절). 일 1회 배치라도 소스/레코드 경계를 길게 끌지 않는다.

## 8. 실패했을 때 — 원인 종류로 안내를 가른다

롤백은 데이터만 깨끗이 한다. **"다음에 뭘 해야 하는가"는 알려주지 않는다.** 원인의 종류로 안내를 가른다(상태코드·`code` 매핑은 `api-spec.md §0`).

- **일시적 실패**(락·타임아웃·외부 API 지연) → 재시도. ingest는 timeout+재시도 N회.
- **입력 형식 오류** → `400 INVALID_PARAM`(서빙 API). 재시도해도 같다.
- **리소스 없음** → `404 NOT_FOUND`.
- **서버 귀책** → `500 INTERNAL`. 불투명 메시지로 묻지 말고 로그를 남긴다(rules-full §8).

## 9. 테스트 (testing.md와 연결)

- 멱등성·UNIQUE 제약·pg_trgm처럼 **DB 동작 자체가 검증 대상**이면 실제 DB로 본다(Fake로 빼면 검증 가치 소멸 — `testing.md` 5절).
- DB가 단순 협력자이고 그 위 로직만 보고 싶으면 Fake(인메모리 Repository).
- 일 1회 배치는 시각·외부 응답을 주입 가능하게 만들어, 배치 한 번의 결과(신규/갱신/스킵 건수, 멱등)를 검증한다.
