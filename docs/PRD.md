## 1. 개요

### 1.1 문제 정의
정부 창업 지원금은 많지만 흩어져 있고, 예비·극초기 창업자는 (1) 자신이 자격이 되는지 모르고(특히 사업자등록 전), (2) 공고 용어(사업화자금·업력 등)가 어렵고, (3) 신청 방법을 모른다. 기존 모아보기 서비스는 사업자 보유를 전제해 첫 화면부터 막힌다. 정보 나열이 아니라 **진입장벽 제거**가 필요하다.

### 1.2 제품 한 줄 요약
> 예비·극초기 창업자와 대학생을 위한, 내 단계에 맞는 지원금만 골라주는 **지원금 전담 비서**.

### 1.3 타겟 사용자
- **주 사용자**: 예비 창업자(사업자등록 전) · 극초기 창업자(업력 3년 미만) · 창업에 관심 있는 대학생
- **부 사용자**: 바이브코더(개발자 예비창업자) — 별도 페르소나 아님, "예비/초기 + 기술·R&D 카테고리" 조합으로 커버

## 2. 목표와 비목표

### 2.1 Goals (MVP, 측정 가능)
1. 3개 공공 소스(K-Startup 전량 / 기업마당 `searchLclasId=06` / 온통청년 `mclsfNm=창업`)를 **일 1회 배치로 수집**하는 파이프라인 가동. 재실행 멱등(UPSERT), 필수필드 누락 레코드는 스킵+로그.
2. **페르소나 4탭(예비/대학생/초기/전체)이 쿼리로 정확 작동.** K-Startup 공고의 `target_*` 채움률 ≥ 95%(구조화 필드 기반이라 가능).
3. **dedup 오합치 0** (출시 전 표본 50쌍 수동 검수 기준). 중복 공고는 canonical 1건만 리스트 노출.
4. **event_log를 서비스 오픈 1일차부터 적재** — 아하 선행지표(공고 상세 진입→원문 클릭률, 찜율)를 측정 가능한 상태로.
5. 공고 상세 페이지가 **검색엔진에 색인**됨(SSG/ISR, 메타태그 완비).

### 2.2 Non-Goals ⚠️
1. **로그인(OAuth) 지원 — In-Scope로 확장**(팀 3인 합의). 단 **익명 사용도 계속 기본** — 로그인은 서버측 찜 동기화 등 선택 기능이며 로그인 없이도 전 기능을 쓸 수 있다. 개인화·추천은 여전히 Phase 3.
2. **AI 추천 없음** — MVP는 규칙 기반 필터만.
3. **민간 공고 수집 — In-Scope로 확장**(2026-07-26, 팀 3인 합의 — FR-010). 단 **하이브리드 한정**: 화이트리스트 소스를 Tier 1 기술(정적 HTTP+RSS)로만 수집하고, **사람 검수·페르소나 태깅을 거쳐야 게시**된다. 전수 크롤링·집계 사이트 크롤링·헤드리스 브라우저는 여전히 금지(기획서 가드레일 5).
4. **공공기관 추가 소스 탐색 없음** — 표본 검증으로 3대 API가 공공 영역을 닫음을 확인(기획서 §6). R&D(SMTECH·과기부)·중소벤처24는 Phase 2.
5. **알림(이메일/푸시) 없음.**
6. **세무·법인전환 콘텐츠 없음** — "지원금 전담" 범위 유지.
7. 중소기업 종합 포털화 금지 — 타깃은 예비~초기 창업.

- 다국어

## 4. 기능 요구사항

### FR-001: 공고 수집 파이프라인 (Python)

| 항목 | 내용 |
|---|---|
| 우선순위 | Must |
| 연결 AC | AC-001 ~ AC-005 (`AC.md`) · 매핑 상세는 `data-model.md` §6/6-B/6-C |

**유저 스토리**
> 운영자로서, 매일 최신 공고가 자동 반영되도록, 3개 API를 수집·정규화해 DB에 적재한다.

**상세 동작**
1. 입력: K-Startup(JSON, 전량) / 기업마당(RSS·XML, `searchLclasId=06`) / 온통청년(JSON, `mclsfNm=창업`)
2. 처리: 소스별 매핑(`data-model.md` §6, 6-B, 6-C) → 표준 enum 정규화(§7) → `(source, external_id)` UPSERT
3. 출력: `opportunity` 갱신 + 수집 리포트 로그(신규/갱신/스킵/미지값 건수)

**엣지 케이스 ⚠️**

| 상황 | 기대 동작 |
|---|---|
| 필수필드(`external_id`/`title`) 누락 | 해당 레코드 스킵 + 로그 (파이프라인 중단 금지) |
| 기업마당 JSON 깨짐 | 애초에 RSS(XML)로 수집 (data-model 6-B 규칙) |
| 미지의 category/enum 값 | `기타`로 적재 + 원본값 로그 (열린 enum) |
| 날짜 형식 이탈("~" 누락, 빈값) | 해당 필드 NULL + raw 보존, 상시(`is_always_open`) 판정 규칙 적용 |
| API 응답 실패/타임아웃 | 소스 단위 재시도 N회 → 실패 시 해당 소스만 건너뜀(다른 소스는 진행) + 실패 로그 |
| 재실행(같은 날 2회) | UPSERT로 멱등 — 중복 행 생성 금지 |
| 공고가 API에서 사라짐 | 삭제하지 않음(이력 보존), `updated_at`만 갱신 안 됨 (data-model §2 — 매 UPSERT 갱신 컬럼) |

### FR-002: dedup & 페르소나 부여 배치

| 항목 | 내용 |
|---|---|
| 우선순위 | Must |
| 연결 AC | AC-006 ~ AC-010 (`AC.md`) · 설계는 `data-model.md` §6-D |

**유저 스토리**
> 사용자로서, 같은 공고가 출처만 다르게 2~3번 보이지 않고, 기업마당 공고도 내 페르소나 탭에 잡히길 원한다.

**상세 동작**
1. 수집 직후 1패스: 정규화 키 생성 → 마감일 블로킹 → 스코어링(0.6 제목 + 0.25 기관 + 0.15 기간, 임계 0.85) → Union-Find 그룹핑 → `dedup_group_id` 부여
2. canonical 선정: K-Startup 우선 → `is_canonical` 설정
3. 페르소나 3단계: 구조화(K-Startup 직접) → 상속(그룹 공유) → 텍스트 키워드 규칙(기업마당 잔여분)

**엣지 케이스 ⚠️**

| 상황 | 기대 동작 |
|---|---|
| 유사하지만 다른 공고(차수만 다름 등) | 보수적 임계(0.85)로 미병합 — **오합치 > 놓침** 원칙 |
| 오합치 발견 | 그룹 해제 가능해야 함(비파괴 — 원본 레코드 불변) |
| 페르소나 신호 없음 | `target_*` NULL 유지 → 화면 "조건 미상" (억지 채움 금지) |
| canonical 공고만 마감, 그룹 내 타 출처는 진행 중 | 재배치: 진행 중 레코드를 canonical로 승격 (배치마다 재평가) |
| 그룹에 K-Startup 없음(기업마당끼리) | 정보량 많은 쪽 canonical |

### FR-003: 페르소나 필터 공고 리스트 (공고 탐색)

| 항목 | 내용 |
|---|---|
| 우선순위 | Must |

**유저 스토리**
> 예비창업자로서, 가입 없이 탭 한 번으로 내가 자격이 되는 공고만 보고 싶다.

**상세 동작**
1. 지원 대상 선택 4종: 예비(`PRE_STARTUP`) / 대학생(`UNIV_STUDENT`) / 초기(`LT_1Y~LT_3Y`) / 전체 — UI는 필터 드롭다운(탭 → 드롭다운, 2026-07-04 QA. 무가입·선택 한 번은 동일)
2. 보조 필터: 지역 · 카테고리(11종+기타) · 진행상태. 정렬: 마감임박순(기본)/최신순
3. 카드: title·organization·category·region·D-day·"사업자 불필요" 배지·출처. `WHERE is_canonical` + status는 조회 시 계산

**엣지 케이스 ⚠️**

| 상황 | 기대 동작 |
|---|---|
| 결과 0건 | 빈 상태 화면: "조건에 맞는 공고가 없어요" + "전체 공고 보기"(필터 초기화) 유도 |
| `target_*` NULL 공고 | persona 필터에서 제외, 지원 대상 미지정(전체) 조회에서만 노출 + "조건 미상" 표기 |
| 마감 지난 공고 | 기본 제외(진행상태 필터 "전체" 선택 시에만 노출) |
| deadline NULL(상시) | "상시모집" 배지, 마감임박순에서 맨 뒤(NULLS LAST) |
| 페이지 범위 초과 | 빈 배열 + 정상 응답(에러 아님) |

### FR-008: 지원금 규모 추출 (데이터 파트 — 서빙·표시는 후속)

| 항목 | 내용 |
|---|---|
| 우선순위 | Should (스코프 확장 승인 2026-07-18 — 이번 단계는 **apps/ingest 데이터만**, api·web 노출은 후속) |
| 연결 AC | AC-028 ~ AC-030 (`AC.md`) · 추출 규칙은 `data-model.md` §6-E |

**유저 스토리**
> 사용자로서, 공고마다 "최대 얼마 규모"인지 한눈에 보고 클릭할지 판단하고 싶다.
> 팀으로서, "지금 신청 가능한 공고의 확인된 지원 규모 총합"을 마케팅 지표로 쓰고 싶다 — 소스가 늘수록(민간 수집 Phase 2 포함) 이 총액이 커지는 것 자체가 서비스 성장의 근거가 된다.

**왜 (마케팅 맥락)**
높은 지원금은 가장 강한 클릭 훅이다. 단 이 가치는 **숫자가 정확할 때만** 성립한다 — 틀린 금액 하나가 서비스 신뢰 전체를 깎는다. 그래서 추출은 채움률보다 정밀도를 우선한다(오추출 > 미추출 금지 원칙). 확인된 것만 보여주는 보수 전략은 마케팅에도 유리하다: 집계 총액이 "최소 이만큼"이라는 하한선이 되어 과장 논란 없이 쓸 수 있고, 추출원이 늘 때마다 총액이 상승하는 성장 서사를 만든다.

**상세 동작**
1. 컬럼 2개(원 단위 정수): `max_support_amount`(**기업당/1인당 최대 지원액** — 사용자 훅), `total_program_budget`(**사업 전체 예산** — 규모 비교·집계용). 원문 표기는 `support_amount`(TEXT)에 보존 — **주의: 이 TEXT 컬럼은 기존 상세 API·상세 페이지("지원 규모 · X")에 이미 연결돼 있어 채우는 즉시 사용자에게 노출된다**(api·web 변경 없이). 표기가 "최대 X원" 사실 서술이라 가드레일을 충족하므로 의도된 효과로 승인 — 신규 숫자 컬럼의 노출(카드 강조·집계 지표)만 후속.
2. 추출: 공고 본문(summary)에서 **확실한 패턴만** 정규식 추출(`data-model.md` §6-E). 수식어("기업당·팀당·1인당·최대" vs "총 사업비·총 예산")로 두 컬럼을 구분한다.
3. dedup 그룹 상속: 그룹 내 한 출처에서 금액이 추출되면 페르소나 상속과 같은 방식으로 그룹에 공유 — K-Startup(본문에 금액이 거의 없음)의 채움률을 교차 소스가 보완한다.
4. 신호가 없으면 **NULL 유지** — 억지 채움 금지(절대규칙 8 준용). 라이브 실측(2026-07-18): 진행중 공고 기준 채움 가능 비율 약 5%(기업마당 18%·온통청년 8%·K-Startup 0.6%) — K-Startup은 금액이 첨부파일(HWP)에만 있는 구조.

**엣지 케이스 ⚠️**

| 상황 | 기대 동작 |
|---|---|
| 자격 조건 금액("매출액 10억 이하"·"1천만원 이상 투자 유치") | **추출 금지** — 지원금으로 오인하면 최악의 오정보. 지원 문맥 수식어가 있을 때만 추출 |
| 단위 혼재("50백만원"·"1.5억원"·"1억 5천만원") | 확실히 파싱되는 표기만 변환, 모호하면 NULL + raw 보존 |
| 범위 표현("5천만~1억원") | 상한값을 `max_support_amount`로 |
| 융자·보증 한도("보증한도 20억") | MVP에선 추출 제외(지원금과 성격 다름) — 원문은 raw에 있음 |
| 재실행 | 같은 본문 → 같은 결과(결정적), UPSERT 멱등 |

**가드레일 (마케팅 사용 시 — 가드레일 1·9 연장)**
- 카피는 **"최대 X원 규모" 사실 서술**까지만. "X원 받을 수 있어요"류 **수령 보장 표현 금지**(선정 여부는 별개).
- 집계 지표는 "금액이 확인된 공고 기준"임을 병기 — 채움률이 낮은 동안 총액을 전체인 양 표현하지 않는다.

**Phase 2 (이번 스코프 아님 — 커버리지 확장 경로)**
- K-Startup 첨부파일(HWP)·상세페이지 추출: **크롤링 금지 원칙(기술 제약 §6)과 충돌** — 원칙 개정(3인 합의) + 파싱 의존성 추가가 선행돼야 함. 이번 실측 0.6%가 data-model "커버리지 갭 실증 시 재검토" 조건을 충족하므로 후보로 기록.
- 민간 공고 수집(Non-Goal 3)과 결합 시 총액 지표 성장 — 같은 추출 파이프라인 재사용.

### FR-010: 민간 공고 수집 — 하이브리드 (크롤러 수집 → 사람 검수 → 게시)

| 항목 | 내용 |
|---|---|
| 우선순위 | Should (스코프 확장 2026-07-26, 팀 3인 합의 — Phase 2 진입. 원안 "수작업 30~50건"을 하이브리드로 대체) |
| 연결 AC | AC-034 ~ AC-039 (`AC.md`) · 소스 매핑·검수 상태·편입 체크리스트는 `data-model.md` §6-F·소스 레지스트리 |

**유저 스토리**
> 사용자로서, 정부 포털에 없는 민간 재단·기업의 지원 프로그램도 한곳에서 보고 싶다.
> 팀으로서, 공공 API가 못 잡는 민간 롱테일이 아하 모먼트의 연료다(기획서 §4 데이터 역설) — 상시 유입 경로를 만들되, 큐레이션 기준과 데이터 정확성은 사람이 지킨다.

**왜 하이브리드인가**
- 민간 공고는 기수제(배치)가 지배적 — 소스당 연 1~5건(2026-07-26 리서치 실측). 수작업 등록(원안)은 마감과 함께 몇 주면 부패하는 스톡이고, 전자동 게시는 큐레이션 기준("무명+적합")과 마감일 정확성(가드레일 2)을 기계가 보증 못 한다. → **크롤러는 감지, 사람은 판단.** 검수 부담은 주당 몇 건 수준이라 지속 가능.
- 소스 실사(2026-07-26, 후보 7곳): robots 전면 금지 1곳·서면 허가 요구 1곳·봇 차단 관측 1곳·JS 렌더링 1곳·게시판 없음 1곳 — **Tier 1로 깨끗하게 수집 가능한 곳은 소수.** 소스 확장은 전수 탐색이 아니라 편입 체크리스트 기반 선별로만 한다.

**상세 동작**
1. **파일럿 화이트리스트 4소스** (편입 근거·external_id 체계는 data-model §6-F):

| source | 기관 | 성격 | 수집 지점 |
|---|---|---|---|
| `asan-nanum` | 아산나눔재단 | 예비·20대·아이디어 단계(두어스·정주영 창경) | `/notice` 게시판 (정적, robots 전면 허용) |
| `kakao-impact` | 카카오임팩트 | 소셜·테크 혁신가 | `/news` 게시판 (정적) |
| `sopoong` | 소풍벤처스 | 기후테크 초기팀 | `/contents` 게시판 (정적) |
| `kb-innovation-hub` | KB이노베이션허브 | 협업형(연 1~2회) | 공고 페이지 (정적, robots 전면 허용) |

2. **기술은 Tier 1 한정**: requests + BeautifulSoup4 + feedparser(정적 HTML·RSS). **예절 의무**: 매 실행 robots.txt 확인 · 식별 UA(`changmun-bot/1.0; +https://changmun.com/bot`) · 요청 간 딜레이 ≥1초 · 일 1회 배치. 403/429·robots 불허 시 해당 소스 스킵+리포트 — **우회 금지, 차단 반복 시 소스 제외.**
3. **수집분은 `review_status='pending'`으로 적재** — 리스트·검색·상세·`ids=`·홈 지표(stats)·상세의 `otherSources` 등 **모든 서빙 경로에서 미노출**(카운트에도, 승인 공고의 형제 목록에도 불포함). NULL(=공공) 허용은 **DB CHECK 제약이 공공 3소스로 한정** — 민간·신규 source가 상태를 빠뜨리면 INSERT 실패(검수 게이트 우회 차단, data-model §6-F 규칙 2).
4. **CLI 검수**(`apps/ingest`, 관리자 웹 UI 아님): pending 목록 → 건별 승인/반려 + **페르소나 수동 태깅**(단계 자체는 필수, 값은 '미상'(NULL 유지) 선택 가능 — 절대규칙 8 양립) + 금액 확인. 승인 → `'approved'` → 기존 서빙·dedup·금액 추출(§6-E) 파이프라인에 합류.
5. **재수집 UPSERT는 내용 필드만 갱신** — `rejected`·`pending`은 `review_status` 불변(반려 공고가 재수집으로 부활 금지). 단 **`approved` 건의 핵심 필드(마감일·모집시작일·제목·금액 표기)가 바뀌면 `pending`으로 되돌려 재검수**한다(AC-039) — 승인은 "그 시점 내용"에 대한 승인이라, 변경된 마감일이 무검증으로 노출되면 가드레일 2가 깨진다.
6. **본문 전문 미수집** — 제목·기관·기간·금액·대상·원문 URL 등 **사실 필드만** 수집·저장(민간 공고문은 공공누리 없는 저작물 — 전재 리스크). 상세 화면은 원문 링크 중심.
7. **소스 발굴 루프**: 집계 사이트(THE VC·올콘·링커리어 등)는 **크롤링 금지**(DB권 리스크 — 잡코리아-사람인 판례 구조) — 사람이 열람해 주최기관을 발굴하고, 그 기관 사이트를 체크리스트(data-model)로 편입한다.
8. **뉴스레터 채널(보조·수동)**: 게시판 없이 뉴스레터로만 알리는 소스(스파크랩 등)는 구독(명시적 수신 동의)으로 후보를 받아 검수 큐에 수동 등록 가능. 단 **그 소스가 먼저 소스 레지스트리 + `source` enum에 정식 편입**(체크리스트 6항목 + 3인 합의)돼 있어야 한다 — enum 밖 임시값을 쓰면 api-spec `source` 계약이 깨지고(같은 값 필터 요청이 400), 기존 소스명을 빌려 쓰면 출처 표기가 틀어진다. 미편입 소스는 등록하지 않고 백로그 유지. **수동 등록도 `pending` 필수** — 크롤러 경로와 동일한 검수 게이트를 통과한다(CHECK 제약으로 강제).

**엣지 케이스 ⚠️**

| 상황 | 기대 동작 |
|---|---|
| robots.txt 불허 / HTTP 403·429 | 해당 소스 요청 중단·스킵 + 리포트 사유 기록(다른 소스 격리 — FR-001 준용). 우회 시도 금지 |
| 파싱 결과 0건(사이트 개편 의심) | 배치는 계속, 리포트에 "0건 — 파손 의심" 경고(조용한 파손 금지 — AC-038) |
| 공공 3종과 중복 게재(금융권 공고 등) | dedup(§6-D)이 처리 — canonical은 공공 우선, 민간 레코드는 그룹 멤버로 유지 |
| 반려(rejected) 공고가 다음날 재수집됨 | rejected 유지 — 내용만 갱신, 검수 큐에 재등장 금지 |
| 승인된 공고의 마감일이 원문에서 바뀜 | 내용 갱신 + `pending`으로 되돌려 **재검수까지 노출 중단**(AC-039). 며칠 미노출 < 틀린 마감일 노출. 그 건이 그룹 canonical이었으면 남은 승인 멤버로 재선정(그룹째 사라짐 방지) |
| 검수 중 배치가 같은 행을 갱신 | 승인·반려 모두 `updated_at` 불일치로 취소 → 재검수. 특히 반려는 불변이라 못 본 내용이 영구 반려로 굳는 것을 막는다 |
| 공공과 중복인 민간 건을 승인 | 승인 트랜잭션 안에서 dedup·canonical 확정 — 배치를 기다리는 사이 중복 노출되는 구간 없음(data-model §6-F 규칙 8) |
| 사이트가 마감일을 명시하지 않음 | NULL(UNDATED) — 크롤러·검수자 모두 억지 추정 금지 |
| 검수 적체(pending 누적) | 서비스에는 무노출이라 품질 영향 없음 — 리포트에 pending 잔량 표기로 가시화 |

**가드레일 (가드레일 5 정밀화 준수)**
- 화이트리스트 밖 소스 수집 금지 — 신규 소스는 편입 체크리스트 전 항목 통과 + 3인 합의.
- 큐레이션 기준은 기획서 §4("타깃이 모를 무명+적합") — 유명 대형 위주로 쏠리면 소스 구성 재검토.
- 민간 공고 카피에도 가드레일 1(합격 보장 표현 금지) 동일 적용.

**Phase 확장 (이번 스코프 아님)**
- **Tier 2**(사이트 내부 JSON 엔드포인트 직접 호출): 소스별 ToS 검토 기록 + 3인 합의로 개별 승인. **Tier 3**(Playwright 헤드리스): 정적으로 못 긁는 고가치 소스가 실증되면 재론(EC2 부하·유지보수 비용 포함 판단).
- 소스 백로그: 브라이언임팩트(게시판 없음 — 프로그램 페이지 변경 감지 방식 필요) · 디캠프(봇 차단 관측 — 정중한 UA로 재확인 후 판단) · 프라이머(robots에 서면 허가 요구 — 허가 요청 메일이 선행) · 롯데벤처스·드림플러스·신한 스퀘어브릿지(Tier 2 후보) 등.

## 7. 데이터 모델 & API 개요

### 7.1 핵심 엔티티 (상세: `data-model.md` — LOCKED)
- **opportunity**: 공고 원장. `(source, external_id)` UNIQUE. 페르소나 컬럼 `target_startup_stage[]`·`target_audience_type[]`, dedup 컬럼 `dedup_group_id`·`is_canonical`, 민간 검수 컬럼 `review_status`(FR-010 — NULL=공공), 원본 `raw JSONB`
- **glossary**: 용어 사전 (term, description)
- **event_log**: 행동 로그 (append-only)
- `app_user` — 로그인 In-Scope로 당김(data-model §8, 구현). (Phase 3) user_stage_history

**관계**: opportunity 1:N event_log(약결합, FK 강제 안 함) / glossary는 독립(텍스트 매칭)

### 7.2 주요 API (상세: `api-spec.md`)

| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| GET | /api/v1/opportunities | 리스트 (persona, region, category, status, q, ids, sort, page, size) | N |
| GET | /api/v1/opportunities/{id} | 상세 | N |
| GET | /api/v1/glossary | 용어 사전 전체 | N |
| POST | /api/v1/events | 행동 로그 적재 | N(익명 ID) |

status·D-day·배지 플래그는 **서버가 계산해 응답에 포함**(프론트 재계산 금지).
