# 기획안 — 쇼케이스 (창업자 제품 홍보의 장) · DRAFT

> **상태: 합의 전 초안.** 팀 3인 합의 후 PRD(FR-010~)·data-model·api-spec·AC에 반영한다.
> 작성: 2026-08-01. 발의: 동희(사장님) — "1인 창업자가 자기 서비스·제품을 홍보할 수 있는 장 + 추후 펀딩".

---

## 1. 왜 (배경)

- 1인·초소형 창업이 계속 늘어난다. 이들은 **알릴 채널이 없다** — 창문에 이미 모여 있는
  예비·초기 창업자·대학생이 서로의 첫 사용자·첫 응원자가 될 수 있다.
- 창문의 순환 구조가 완성된다: **지원금 발견(현재) → 창업 → 제품 출시 → 쇼케이스에서 공개
  → 커뮤니티 반응 → (추후) 펀딩**. 방문 이유가 "공고 확인"에서 "생태계 참여"로 확장된다.
- 기획서 수익모델("초기 무료+광고")과 연결 — 단, MVP는 **전면 무료**. 유료화(상단 노출 등)는
  물량이 생긴 뒤 별도 결정.

## 2. 컨셉

- 가칭 **쇼케이스**(이름 후보: 진열창·새 창·런치). "창문 밖에 내 제품을 진열한다"는 브랜드 결.
- 로그인한 창업자가 자기 제품/서비스를 등록하고, 별도 지면에서 모아 본다.
- **정부 공고 리스트와 완전 분리** — 공공 데이터 큐레이션의 신뢰를 지키는 1원칙.
  쇼케이스 글이 공고 리스트·검색 결과에 섞이지 않는다.

## 3. MVP 스코프 (팀 합의로 확정)

| # | 기능 | 내용 |
|---|---|---|
| S-1 | 제품 등록 | 로그인 필수. 이름·한 줄 소개·설명·대표 링크·이미지 1장·카테고리·(선택) 팀 소개. 등록 즉시 `검수 중` |
| S-2 | 리스트/상세 | 전용 탭(사이드바·Nav에 "쇼케이스" 추가). 승인된 제품만 노출. 상세 = 등록 정보 + 응원 수 + 댓글 |
| S-3 | 응원하기 | 로그인 사용자 1제품 1응원(토글). **무결제 신호** — 추후 펀딩의 수요 검증 데이터 |
| S-4 | 댓글 | 로그인 사용자 텍스트 댓글. 작성자 삭제 가능. 운영 신고는 MVP에선 이메일 접수 |
| S-5 | 주간 모아보기 | "이번 주 새로 열린 창" — 최근 7일 승인작 + 응원순 정렬. 홈에 섹션 1개 노출(공고 섹션과 시각적으로 구분) |

### 검수 운영: 선검수 후게시 (확정)
- 등록 → `PENDING` → 팀 승인 시 `APPROVED` 공개 (거절 시 `REJECTED` + 사유 한 줄).
- **결정 필요**: 승인 도구. (a) DB 직접 UPDATE(도구 0, 완전 수동) vs (b) 팀 전용 최소 승인
  페이지 1장(목록+승인/거절 버튼 — 현 PRD의 '관리자 UI Out-of-Scope' 해제 필요).
  초기 물량 고려 시 (a)로 시작해도 되나, 주 10건 넘으면 (b)가 현실적.
- 댓글은 **후검수**(신고 접수 시 처리) — 댓글까지 선검수하면 대화가 죽는다.

## 4. Out-of-Scope (MVP에서 하지 않는 것)

- **펀딩/결제 일절** — 후원·크라우드펀딩형은 자본시장법·전자금융거래법·크라우드펀딩 중개업
  등록 등 규제 검토가 선행돼야 한다. 로드맵 §7 참고.
- 광고주 영업형 배너/스폰서 지면(별개 주제 — 필요 시 별도 기획).
- 알림(응원·댓글 알림), 팔로우, 프로필 고도화, 검색 내 쇼케이스 혼합 노출.

## 5. 데이터 모델 초안 (data-model.md LOCKED — 3인 합의 필요)

```
showcase_product
  id BIGSERIAL PK
  owner_user_id BIGINT NOT NULL → app_user(id)
  name VARCHAR(80) NOT NULL
  tagline VARCHAR(120) NOT NULL          -- 한 줄 소개
  description TEXT NOT NULL
  url VARCHAR(500)                       -- 대표 링크
  image BYTEA / image_type VARCHAR(30)   -- 프로필 이미지와 동일 방식(1MB 제한)
  category VARCHAR(30) NOT NULL          -- enum: 앱/웹서비스·커머스·콘텐츠·로컬·기타(확정 필요)
  status VARCHAR(10) NOT NULL            -- PENDING | APPROVED | REJECTED (쇼케이스 전용 —
                                         -- 공고의 '저장 금지 status'와 무관한 별개 컬럼)
  reject_reason VARCHAR(200)
  created_at / approved_at / updated_at

showcase_cheer                            -- 응원 (1인 1제품 1응원)
  product_id / user_id 복합 PK, created_at

showcase_comment
  id PK, product_id, user_id, body VARCHAR(1000), created_at, deleted_at(소프트 삭제)
```

- PII 원칙 유지: 노출되는 것은 제품 정보뿐. 작성자는 닉네임 없음 → **표시명 결정 필요**
  (이메일 마스킹? 등록 시 팀명 입력? — 팀명 입력 권장).
- event_log 화이트리스트에 쇼케이스 이벤트 키 추가(익명 원칙 동일).

## 6. API 표면 초안 (api-spec.md 반영 전)

```
POST   /api/v1/showcase                     등록(로그인, multipart) → 202 PENDING
GET    /api/v1/showcase?sort=cheers|latest&category=&page=   승인작 리스트
GET    /api/v1/showcase/{id}                상세(승인작만 200, 그 외 404)
PUT    /api/v1/showcase/{id}                본인 수정 → 재검수(PENDING)
DELETE /api/v1/showcase/{id}                본인 삭제
PUT    /api/v1/showcase/{id}/cheer          응원 토글(로그인)
POST   /api/v1/showcase/{id}/comments       댓글(로그인)
DELETE /api/v1/showcase/comments/{id}       본인 댓글 삭제
GET    /api/v1/showcase/weekly              주간 모아보기(최근 7일 + 응원순)
```
- 에러·필드 규칙은 api-spec 기존 형식(RFC7807+code, camelCase) 그대로 따른다.

## 7. 로드맵 (펀딩 — 방향만 합의)

| Phase | 내용 |
|---|---|
| 1 (MVP) | 위 §3. 응원 수 = 수요 신호 축적 |
| 2 | 신고/차단, 알림, 제품 업데이트 로그("개발 일지"), 검색 연동 |
| 3 (펀딩) | **후원/크라우드펀딩형**. 직접 중개업 등록 vs 기존 플랫폼(와디즈·텀블벅) 연동 위탁을
  법률 검토 후 결정. 응원 데이터로 "펀딩 열 자격"(예: 응원 100+) 게이팅 |

## 8. 가드레일

1. 공고 리스트·검색과 섞지 않는다(전용 지면만). 공공 큐레이션 신뢰가 본체다.
2. 쇼케이스 카피에도 합격·수익 보장류 표현 금지 원칙 준용.
3. MVP는 무료·무결제 — 돈이 오가는 기능은 규제 검토 전 금지.
4. 개인정보 최소: 제품 정보만 공개, 계정 정보 비노출(표시명은 별도 입력).
