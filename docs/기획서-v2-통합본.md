# 창업 지원금 비서 — 기획서 v2

**한 줄 정의:** 예비·초기 창업자가 내 창업 단계에 맞춰 받을 수 있는 지원금을 골라주는 **지원금 전담 비서**.
**문서 성격:** 팀 공유 + AI 작업 지시용(결정 + 이유). **상태:** 포지셔닝·스택·데이터 모델 확정 / 사용자 검증 전.

---

## 1. 문제
지원금은 많지만 흩어져 있다. 우리 타깃(예비·극초기)의 진짜 장벽은 위치가 아니라:
1. 내가 자격이 되는지 모른다(특히 사업자등록 전)
2. 용어가 어렵다(사업화자금·업력 등)
3. 신청 방법을 모른다

→ 정보 나열이 아니라 **진입장벽 제거**가 핵심.

## 2. 타깃
예비·극초기 창업자·대학생. 자본·정보·경험 모두 부족.
**원칙: 진입은 좁게, 비전은 길게.** 예비에서 신뢰를 얻고 개인사업자→법인 성장에 동행. 기존 사업자는 경로가 있어 후순위. IT 특화는 필터로 쓰지 않음(모수 축소).

## 3. 경쟁과 빈틈
"모아보기"는 레드오션·기본기. 공공 오픈API라 데이터 자체는 해자 아님. 빈틈:
- 엑시토 2.0이 B2B로 이동 → 예비창업자 후순위
- 기존 필터는 사업자 전제 → 사업자 없는 사람은 첫 화면부터 막힘
- 용어 미해석, "사업자 없어야 받는 돈"이 묻힘

**해자 우선순위(못 박음):**
1. **동행·솔직한 전환 안내** — 정부가 구조적으로 못 함(리텐션이 KPI 아님). 편집 방침·신뢰라 베끼기 어려움 = 진짜 해자.
2. **용어 풀이** — 온보딩 기능(LLM이면 생성 가능, 단독 해자 아님). 방어력은 편집 품질.
3. **기억·개인화** — 정부도 시도 중. 기본 기대치, 단독 의존 금지.

## 4. 제품 = 입구 + 자물쇠
입구가 사용자를 데려오고, 자물쇠가 붙잡는다.

**[입구] 모아보기** (공공 + 민간)

| 기능 | 설명 |
|---|---|
| 페르소나 필터 | 첫 화면 4탭(사업자 없음/예비/대학생/사업자 보유). 최우선 차별점 |
| 용어 풀이 | 공고 용어를 초보 눈높이로. API에 없어 자체 생성 |
| 마감 알림 | D-day·마감순 정렬 |

+ "사업자 불필요" 배지.

> **페르소나 필터는 K-Startup 한정으로 작동한다.** bizinfo·민간은 구조화 필드가 없어, 수동 태깅 전까지 필터 없이 노출. 전 출처 균일 작동인 척하지 않는다(가드레일 2와 직결).

**[자물쇠] AI 비서:** 행동 추적 + 최소 입력 → 단계에 맞는 추천, 단계 전환 기억·안내.

> **아하 모먼트:** 몰랐던 지원금을 추천받아 실제 수령. 단 수령은 수개월·통제 밖 → **선행지표(몰랐던 공고 찜/신청클릭률)로 검증.**

> **데이터 역설:** 아하의 연료(롱테일 민간)가 가장 모으기 어려운 데이터. → MVP 수작업 30~50개를 **"타깃이 모를 무명+적합 공고"**로 큐레이션(유명 대형 금지). 선정 기준이 곧 초기 차별점. 민간 등록 시 페르소나 수동 태깅 필수.

## 5. 가드레일 (위반 시 반려)
1. **추천 ≠ 선정.** "신청 자격이 됩니다 / 합격은 별개". 과한 약속 금지.
2. **데이터 정확성 > 추천.** 마감일·자격 틀리면 신뢰 즉사.
3. **개인화는 최소 입력.** 무가입 페르소나 탭 → 쓰며 축적.
4. **범위는 좁게.** "지원금 전담", 세무·법인전환은 곁다리.
5. **민간 전수 크롤링 금지.** 법적·유지보수 리스크. — **화이트리스트 하이브리드는 예외**(2026-07-26 정밀화, PRD FR-011): robots·약관을 존중하는 소수 선별 소스를 정적 기술로만 수집 + 사람 검수 후 게시. 집계 사이트 크롤링(DB권)·차단 우회·헤드리스 브라우저·전수 수집은 계속 금지.

## 6. 기술 검증 (K-Startup 실데이터 완료)
공고 API(`getAnnouncementInformation01`) 구조화 필드로 필터 매핑:

| 필터 | 필드 |
|---|---|
| 예비 / 사업자 없음 | `biz_enyy` |
| 대학생 / 청년 | `aply_trgt` |
| 지역 | `supt_regin` |
| 마감 | `pbanc_rcpt_end_dt` |

실검증 핵심(설계서만 봤으면 놓침):
- 응답 봉투가 설계서와 다름 → **JSON(`returnType=json`) 사용**
- 날짜 `YYYYMMDD`
- 카테고리 9종이 끝 아님(`판로ㆍ해외진출` 등 + 구분자/HTML 엔티티 혼재) → 열린 enum + 미지값 로깅
- `biz_trgt_age`는 거의 "전 연령" → 필터 무가치
- 예비창업자 포함 6/10건 → 페르소나 필터 유효 확인
- 전체 ~28,944건 → 일 1회 배치 충분

bizinfo는 신청대상·연령 구조화 필드 없음(`trgetNm` 자유텍스트) → 페르소나 필터 미지원. 용어 풀이는 어느 API에도 없음(자체 제작).

### 소스 전략 — 부분집합(창업)에 집중

구조: **기업마당(중기부 본부, 전 부처·지자체 의무수집 = 전체집합) ⊃ K-Startup(창업진흥원, 창업 분야 = 부분집합).** 기업마당은 소상공인·중소·중견 전 영역(R&D·융자·수출·인력 등)을 담아 양은 가장 많지만, 우리 타깃(예비·극초기)과 무관한 공고가 대부분이고 페르소나 필터도 안 받친다. → 전량 수집은 커버리지가 아니라 **노이즈**(가드레일 4 위반).

| 소스 | 정책 | 이유 |
|---|---|---|
| **K-Startup** | **메인 · 전량 수집** | 예비·극초기 타깃 + 페르소나 필터 완전 작동 |
| **기업마당** | **창업분야(`searchLclasId=06`)만 보완 수집** | K-Startup이 놓친 지자체·유관기관 창업 공고만 메움. 나머지 7분야 제외 |
| **온통청년** | **창업 슬라이스(`mclsfNm=창업`)만 보조 수집** | 청년정책 전반이라 창업은 소수. 대상(대학생/청년)은 학력·연령에서 유추 |
| **중소벤처24·R&D(SMTECH·과기부)** | **Phase 2** | API 있으나 기업마당과 중복 가능성 높음 → 중복률 실측 후 |
| **CCEI·테크노파크·지역기관 다수** | **MVP 제외(크롤링 영역)** | API 없음 + 로그인·JS. 공식 창업공고는 K-Startup/기업마당이 커버 |

> **원칙 — 공공 ≠ API 제공.** 정부기관이어도 API 없이 로그인·JS로 막힌 곳은 민간과 동일 취급(크롤링 영역, 나중). 이 기준으로 소스를 단순 분류한다.
> **선행 검증**: 기업마당 `06`(창업)이 K-Startup과 얼마나 겹치는지 실측 → 고유 공고 많으면 보완 확정.
> **dedup 필수**: 같은 공고가 여러 소스에 중복 게재됨(소스 3개) → 제목·기관·기간 유사도 기반 중복 제거를 수집과 동시에. (스키마는 무변경 — `source`+`external_id`+`raw`로 흡수, 대상/지역은 크롤러가 정규화)
> **✅ 공공 소스 탐색 종료(표본 검증 완료).** 기업마당은 중앙부처·지자체·공공기관 560여 곳 정책정보를 법적 통합 → 표본 공고가 전부 K-Startup·기업마당에 중복 존재함을 확인. 공공 정부예산 영역은 3대 API로 닫히므로 **추가 공공기관 API 탐색·크롤링 불필요.** 남은 미개척지는 정부 API가 구조적으로 못 잡는 **민간/자체 자금 롱테일**(MVP 이후).

**핵심: 우리는 전체집합(중소기업 종합)을 노리지 않는다.** 그건 K-Startup·기업마당 본가의 레드오션이다. 우리는 부분집합(창업), 그중 예비·극초기에 집중한다.

**API 스코프:** K-Startup 공고 API(`getAnnouncementInformation01`)만 MVP / 통합공고(지원금액)=Phase 2 / 통계·콘텐츠=제외.

## 7. 아키텍처 & 데이터 모델 (확정)
**스택:** Spring Boot(서빙) · PostgreSQL · Python(수집) · Next.js(프론트, SEO).

```
[Python 수집] →(UPSERT)→ [PostgreSQL] ←(SELECT)← [Spring] →REST→ [Next.js]
```
- 수집은 상시 서버 아님(수동/크론 실행 스크립트). **모노레포 1개**: `apps/web`(Next.js)·`apps/api`(Spring)·`apps/ingest`(Python)·`/docs`·`/db`. (통합 레포로 변경 — 계약·스키마 공유)
- Python↔Java 공유물은 코드가 아니라 **DB 스키마(Flyway)**뿐.

**데이터 규칙:**
- Flyway = 스키마 단일 진실, Spring `ddl-auto=validate`
- `(source, external_id)` UNIQUE + UPSERT → 멱등성 DB가 강제
- status는 저장 안 하고 마감일로 계산(일 1회 갱신이라)
- 정규화·검증은 크롤러 책임

**데이터 모델:** `opportunity`(실데이터 검증 후 LOCKED, 상세는 `data-model.md`). 페르소나 필터 컬럼 = `target_startup_stage[]`(예비=`PRE_STARTUP`), `target_audience_type[]`(대학생=`UNIV_STUDENT`), `region`/`application_deadline`.
비서용 3테이블 추가(opportunity 불변):
- `glossary`(용어) — Phase 1
- `event_log`(행동) — **Phase 1 1일차부터 적재**(소급 불가, append-only)
- `app_user` + `user_stage_history`(단계 동행) — Phase 3

> 민간·bizinfo 공고는 `target_*`가 NULL → 필터 누락. 수작업 등록에 페르소나 수동 태깅 필수.

**개발 방식:** 스펙 우선. 계약 문서(PRD·data-model·taxonomy·api-spec·screens) 근거로 AI 지시. 모호하면 멈추고 합의.

## 8. 획득
- **SEO = 핵심 무료 엔진.** 공개 공고 페이지를 Next.js SSG/ISR로 검색 노출. 배치 갱신이라 ISR 재생성 주기=크롤링 주기로 맞추면 성능+SEO+신선도.
- 시드 채널: 대학 창업동아리·창업지원단·커뮤니티.
- 프론트가 차별화의 거의 전부 → Phase 1 최고 레버리지.

## 9. 로드맵 (3인)

| 단계 | 내용 | 일정 |
|---|---|---|
| 1. 공공 모아보기 | API 연동, 수집·정제, 필터·용어풀이·마감알림, event_log 1일차 | 3~4주(출시) |
| 2. 민간 | 공공에 없는 사업 수집(상시 운영) | 1~2주+ |
| 3. AI 비서 | 행동 활용, 프로필·단계, 추천(규칙→AI), 익명→로그인 전환 | 4~6주 |

**순차 완성 금지: 1번만 먼저 출시해 "사람이 오는가" 검증.** 안 오면 2·3 무의미.
- 2번: 30~50개 수작업(선정기준=§4), 반복가치 큰 소스만 점진 크롤러. 전수 크롤링 금지.
- 3번: 규칙 기반 필터링부터(핵심의 80% 달성), AI는 위에 얹음. 데이터 깨끗해야 시작.

## 10. 팀 분담 (3인 전원 백엔드)
구멍: 프론트 주력 부재 + 초반 백엔드 셋 겹침.

**1번 단계**
- A — 프론트 전향: 필터·용어풀이·마감알림 UI + 행동 로깅 심기. (Phase 1 최고 레버리지라 억지로라도 뺀다)
- B — 데이터·파이프라인: API 연동, 정제, 페르소나 분류 규칙, DB(심장)
- C — API·인프라 + 비서 토대(로깅 설계·프로필 구조)

**2·3번 단계:** A 백엔드 복귀 → 셋 다 크롤링·AI 집중.
**셋이 합의 필수:** 데이터 스키마 변경 / "무엇을 안 만들지"(범위 좁게).
